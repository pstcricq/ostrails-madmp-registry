# dmp-registry

Registry of SOCIB research projects and their machine-actionable DMPs.

Every DMP here is written by a bot, never by hand. Researchers fill in their DMP
in DSW (Data Stewardship Wizard) and click Submit; the submission service commits
the rendered JSON into this repository. Nobody needs a GitHub account to appear here.

## Layout

```
projects/
  <slug>/
    template/
      dmp_project_template.json   the project DMP, may still contain {snake_case} placeholders
    productions/                  deployment DMPs, placeholders resolved
    .meta.json                    identity and status of the project, written by the bot
registry/
  index.json          generated: the list of known projects, consumed by DSW
```

`<slug>` is the project acronym, lowercase, `^[a-z0-9-]{3,32}$` (`canales`,
`endurance-line`). It is a human label, not an identity — see below.

## Identity

The identity of a project is its **DSW project UUID**, recorded in
`projects/<slug>/.meta.json`. The slug can be renamed; the UUID cannot.

When a DMP arrives, the submission service resolves it in this order:

| Situation | Action |
| --- | --- |
| slug known, same UUID | commit into the existing folder |
| slug unknown, UUID unknown | create the folder, write `.meta.json`, commit |
| slug known, different UUID | do not write — open an issue (collision) |
| UUID known under another slug | `git mv` the folder, record the old slug |

A renamed project therefore keeps its history and its link to DSW.

## Integration with DSW

`registry/index.json` is regenerated by CI on every push and is the source of the
project typeahead in the DSW knowledge model. A researcher selects an existing
project (the DMP lands in its folder) or, if their project is not listed yet,
types an acronym and a title — nothing is created until they submit.

## Quality control

CI runs the maDMP quality control on every DMP it receives and records the outcome
in `.meta.json` and `registry/index.json`:

- `pass` — no failing check
- `pass-with-warnings` — optional fields missing, suggested vocabularies not followed
- `fail` — invalid JSON, missing required field, cardinality or cross-field rule broken

A failing DMP is still committed: the artifact is kept so it can be inspected and
fixed. What a failure blocks is downstream use — a project whose template is
`fail` cannot be used to generate deployment DMPs in `productions/`. It never
blocks data acquisition.

`projects/glider-test/` is a fixture used to exercise the pipeline; it is marked
`"fixture": true` in its `.meta.json` and is excluded from `registry/index.json`.

Rules and knowledge model live in
[madmp-core](https://github.com/Pierrott64/madmp-core).
